# 채용공고 디자인 컨셉과 반복 제작 기준

기준일: 2026-09-26. 새 날짜·새 직무의 채용공고를 만들 때 먼저 읽는 문서다. 현재 사용하는 컨셉은 A·B 두 개이며 C·스튜디오 시안은 사용하지 않는다.

| 컨셉 | 핵심 표현 | 상세 명세 |
| --- | --- | --- |
| `editorial-v1` · A 에디토리얼 | 흰 여백, 한글 메시지, 컬러 사진, 차분한 초대 | [A 컨셉 문서](A-editorial.md) |
| `poster-v1` · B 타이포 포스터 | 어두운 바탕, 대형 영문 제목, 흑백 사진, 명암 전환 | [B 컨셉 문서](B-poster.md) |

두 컨셉 문서의 `v1`은 문서와 참고 이미지의 기준 버전이다. 현재 앱에서 자동으로 처리하는 템플릿 버전 필드는 아니다.

## 보관 원칙

- 컨셉 문서는 구성·색상·타이포그래피·말투와 내용 교체 범위를 정의한다.
- `references/*-v1-preview.png`는 2026-09-26의 A·B 상단 이미지를 복사한 고정 참고 자료다. 내보내기 스크립트의 출력 대상이 아니며 새 공고를 만들 때 덮어쓰지 않는다.
- 전체 공고의 현재 구현은 각 컨셉 문서가 연결한 JSX와 CSS에서 확인한다. 미리보기는 상단만 보여주므로 전체 섹션 순서를 대신하지 않는다.
- 디자인 원칙을 변경할 때 문서와 기준 이미지를 함께 갱신한다. 큰 변경은 `v2` 문서·참고 이미지로 별도 보관하고 변경 이유를 기록한다.
- 공고 사실을 바꾸는 일과 디자인 컨셉을 바꾸는 일을 구분한다. 새 회차라는 이유로 색상·폰트·레이아웃을 다시 설계하지 않는다.

## 매 공고에서 준비할 내용

아래 입력 항목은 제작용 체크리스트다. 현재 앱이 이 양식을 그대로 읽는 기능은 없다.

| 입력 | 확인할 내용 |
| --- | --- |
| 공고 식별 | 고유 ID, 실제 등록일, 원문 또는 승인된 채용 내용, 채용 연도 |
| 직무 | 한글·영문 직무명, 전문분야, 경력, 고용형태 |
| 업무 | 업무별 제목·설명. 항목 수는 원문에 맞게 결정 |
| 지원 조건 | 필수 조건과 우대사항을 구분 |
| 근무 조건 | 급여, 수습, 근무시간, 장소, 주소, 교통 안내 |
| 회사 소개 | 역할에 맞는 소개, 확인된 복지, 사용할 사진 |
| 지원 안내 | 전형 단계, 제출 자료, 유의사항 |
| 컨셉별 문구 | A의 한글 제목·소개 / B의 짧은 영문 제목·한글 초대 문장 |
| 접수 정보 | 목록에 표시할 마감일과 채용 시 마감 여부. 게시 이미지 본문과 분리 |

미확인 조건을 지난 공고에서 그대로 가져오지 않는다. 원문에 없는 복지·연봉·업무를 새로 만들지 않는다. A·B는 같은 공고 데이터를 표현하므로 채용 사실은 서로 일치해야 한다.

## 공통 출력 규격

- 화면과 게시 이미지 모두 720 CSS px를 기준으로 한 세로 1열 디자인이다.
- 게시 PNG는 2배 해상도, 가로 1440px로 생성한다. 높이는 내용에 따라 달라지며 고정하지 않는다.
- 게시 이미지 표시 폭은 최대 720px, 모바일에서는 화면 폭에 맞춘다. 360px 표시 기준 주요 본문은 약 16px다.
- `-3x.png`는 호환용 파일명이다. 실제 3배 출력이라는 의미가 아니다.
- 게시 PNG와 사이트용 `-preview.png`를 함께 생성한다. PC·MO용 별도 이미지는 만들지 않는다.
- 9월 10일을 포함한 모든 공고는 `downloads/{공고 ID}/{시안 ID}-3x.png` 경로에 생성한다. 루트의 기존 `VW-*.png` 8개는 이미 배포된 URL을 위해 그대로 보존하며 생성·수정·삭제 대상에서 제외한다. 공고 마감 후 사용자가 직접 정리한다.
- 게시 이미지의 접수 안내는 ‘지원 방법’과 ‘잡코리아 이력서 양식으로 즉시지원’이다. 접수 시작일·마감일·채용 기간·‘채용 시 마감’은 잡코리아의 접수기간 영역에서 관리한다.
- `word-break: keep-all`을 유지하고 어절·역명이 중간에서 끊기거나 조사·어미·짧은 단어만 다음 줄에 남지 않게 조정한다. 줄바꿈은 브라우저만 보지 말고 최종 PNG로 확인한다.

## 현재 구조에서 새 공고 만들기

1. 원문 또는 승인된 채용 내용을 정리하고 A·B 문서에서 유지할 규칙을 확인한다.
2. 기존 공고 JSX는 해당 회차의 기록으로 취급한다. 새 공고용 컴포넌트와 필요한 본문 파일을 `src/pages/` 아래 별도 경로에 만들고 기존 스타일을 재사용한다. 새로운 JSX에는 `main.recruitment.editorial` 또는 `main.recruitment.poster`를 유지한다.
3. [공고 등록 파일](../../src/recruitments.js)에 고유 ID와 메타데이터, `designs`를 추가한다. `component`는 `src/pages/` 아래 확장자 없는 경로로 지정한다. 기존 공고의 이미지 경로·별칭·`legacyImageKey`는 복사하지 않는다.
4. 생성된 공고별 경로와 파일명을 사용한다. 목록·다운로드·HTML·이미지 생성 대상은 이 등록 정보에서 자동으로 연결된다.
5. `npm run export:png`로 생성하고 A·B의 전체 PNG를 720px와 360px 표시 폭으로 검수한다. 본문 크기를 줄이지 말고 문장과 의미 단위 줄바꿈을 다듬는다.
6. 공고 사실의 일치, 누락, 과거 공고의 변경 여부를 확인한다. `node --test scripts/recruitments.test.mjs`와 `npm run build:only`로 등록 구조와 빌드를 검증한다. 필요한 UI 검사는 `scripts/check-common-artwork.cjs`를 사용한다.
7. 새 이미지가 공개 서버에 배포된 뒤 해당 공고의 HTML을 사용한다. 로컬 생성만으로 공개 이미지가 갱신되지는 않는다.

현재는 등록·경로·출력은 공통화되어 있지만, 상세 본문은 JSX에 직접 작성되어 있다. 이 문서 작성으로 ‘내용 데이터만 바꾸면 전체 본문이 자동 생성되는 기능’까지 구현된 것은 아니다.

## 권장하는 다음 개선

반복 제작의 안정성을 높이려면 **컨셉 문서 + 공용 A·B 컴포넌트 + 공고별 내용 데이터 + 기준 이미지 검수**를 함께 운영한다.

- 공용 `EditorialTemplate`과 `PosterTemplate`이 배치와 스타일을 담당한다.
- 공고별 내용 파일 하나가 업무·요건·조건·지원 정보를 담고 두 템플릿에 같은 사실을 전달한다.
- 컨셉별 헤드라인과 소개 문구만 별도 필드로 둔다. 콘텐츠 순서 차이는 템플릿이 처리한다.
- 템플릿에는 버전을 두고, 디자인을 바꿀 때 이전 버전을 유지해 과거 공고가 일괄 변경되지 않게 한다. 공통 CSS도 버전별 범위를 함께 관리해야 한다.
- 긴 직무명·긴 우대사항·항목 수 증가 사례를 테스트하고 최종 PNG를 기준 이미지와 비교한다.

이 구조는 권장 설계이며 아직 구현하지 않았다. 현재 단계에서는 문서에 맞춰 기존 스타일을 재사용하는 방식으로 제작한다.

## 다음 작업에서 사용할 요청문

> docs/design-concepts/README.md와 A-editorial.md, B-poster.md를 읽고 기존 컨셉을 유지해 새 채용공고를 만들어줘. 공고 ID는 [고유 ID], 등록일은 [날짜], 직무는 [직무명]이야. 채용 내용은 [원문 또는 승인된 내용]을 사용해. 기존 공고와 게시 URL은 보존하고 새 공고를 별도로 등록해줘. A·B의 채용 사실을 일치시키고 최종 PNG의 모바일 가독성과 줄바꿈까지 확인해줘.
